## What belongs in E2E

Assert in E2E only what needs the deployed stack: server rendering, auth gating, persistence, provider and webhook round trips, and streaming and navigation handoffs. Put CSS animation, layout geometry, focus, and markup facts in real-browser component tests (`*.browser-acceptance.test.ts` with `shared/testing/playwright-browser.ts`) or `@testing-library/react` tests, and keep only a readiness sentinel in E2E.

Run a check every paid case could repeat, such as post-fulfillment support or reserve-again, on one opted-in case instead of the shared checkout flow.

## Browser session

- New browser code drives `E2EBrowserSession` (`e2e/browser-session.ts`) with native Playwright: `session.use(label, (page) => …)` on the active page and `session.evaluate(label, fn, arg, { timeoutMs })`. Playwright serializes `fn`, so it must not close over anything. Don't add argv commands to the `Runner` in `e2e/runtime.ts`; it is a shim over the session and goes once no caller needs it.
- While a case still runs on the argv `Runner`, get its session with `browserSessionFor(run, sessionId)` (`e2e/runtime.ts`); both then drive the same context. A checkout-pool case gets `run` and `session` from its execute context (`WorkspaceE2ECaseContext` in `e2e/types.ts`), so case factories, binders and identity helpers take no runner; a case identity's `signIn` takes that context. Resolve it inside a step, so a failure to open the browser stays attributed to that step. Reach the context through the page inside `session.use` (`page.context()`), not through the Playwright `Browser`. Cookies go through the session only: `setSessionCookie` for a seeded sign-in and `describeCookie` for a value-free check. `submitCheckoutPayment` (`e2e/checkout/payment.ts`) returns the checkout page it submitted from; when the payment opens another page, make it active again with `session.activate`. The hosted-payment steps still read and switch argv tab ids until they move to the session. An argv tab id stays with its page, so `session.activate` and the argv `tab` command can be mixed.
- Waits that several cases share live in `e2e/browser.ts` and take the session: `openPage` (primes preview access when the run has a bypass secret, then loads the URL), `waitForReactFormSubmit`, `waitForReactHydration`, `waitForReactHandler`, `activateElement` (visible focus, then Enter), `activateHydratedElement` (hydration wait first), `waitForPageCondition` (a self-contained in-page function and its argument), `assertPageCheck` (see below), `readPageText`, `waitForPageText`, `waitForPageTextContent`, `waitForPageUrl`, `readPageUrl`, `waitForPageSnapshot` (polls the body's interactive aria snapshot, redacted) and `scrollIntoView`. `waitForPageText`, `waitForPageSnapshot` and `waitForPageUrl` also take the `browserSessionFor(run, id)` effect itself and resolve it on every read, so a browser that fails to open reads as an unreadable page and the wait runs out, as an argv read that allowed failure did; pass the effect where the argv poll it replaces could meet a browser that never opened. Write other actions natively, one `session.use` per action, so a step deadline that interrupts the step starts no later action. Keep `.filter({ visible: true })` on locators that replace an argv `fill`, `click` or `focus`, which acted only on visible matches. While an argv wrapper still serves unmigrated callers, it sends the session helper's own self-contained in-page function through `wait --fn` or `eval` (`inPageCall` in `e2e/browser-scripts.ts`), so both drivers run one check. The restored reservation form check is `isPrefilledReservation` with `toPrefilledReservation(data)` (`e2e/checkout/prefilled-reservation.ts`); `getPrefilledReservationConditionScript` is its argv form. The reservation form preparation is `prepareReservationForm` with a preparation from `e2e/checkout/reservation-form-preparation.ts`: `toReservationStep(data)` makes the selection on the selection step and fills the contact on the contact step, `toReservationSelectionPreparation(data)` only makes the selection, and `preparedReservationForm` only waits for the enabled action of a form the case prepared itself. Every product's selection lives in that one function because Playwright serializes only the function it is given: it can call the functions it declares inside itself, never a module-scoped helper.
- `waitForPageUrl` and the argv `waitForBrowserUrl` report a URL that never matches as a failure, not a timeout, with the page diagnostics in the message; the diagnostics read is bounded by the argv command default. URLs reach `matches` with registered secrets redacted.
- Write a case's in-page condition as an exported self-contained function beside a builder that computes its argument in Node, such as `isSelectedDurationZeroPrice` and `toSelectedDurationZeroPrice`. Test it in real Chromium against the page shapes it must accept and reject (`*.browser-acceptance.test.ts`). To pin how a step fails, run it as the one step of a C03 case on real Chromium with `runBrowserStep` (`e2e/case-runner.browser.test-utils.ts`) and compare its annotations.
- Write an in-page assertion as a self-contained function that returns why the page is wrong as a code-owned string, or `null` when it holds, and run it with `assertPageCheck(session, label, check, arg, { timeoutMs })`, which fails with `<label> failed: <problem>`. Examples: `findFulfilledStatusPageProblem` and `findRepeatReservationProblem` (`e2e/checkout/repeat-reservation.ts`). Don't throw from the check: the session reports a thrown error only as `<label> failed`.
- `session.evaluate` returns the page's values as they are, while argv output was redacted: pass evaluated text through `redact` before it reaches a failure message or a log.
- `session.evaluate` with `timeoutMs` reports an overrun as a timeout, but the argv `eval` it replaces reported a failure. Wrap a migrated evaluation in `withoutWorkspaceE2ETimeout(label)` to keep it a failure; `assertPageCheck` already does. The wrapper treats every timeout as a failure, so use it only where nothing throws a named `TimeoutError` or a timeout `WorkspaceE2EError` that must stay a timeout. Native steps that ran in `tryWorkspaceE2EPromise` before the session, such as agent booking's consent page, keep a Playwright timeout a failure the same way.
- A case that needs a second browser, such as a signed-out visitor's, reaches it through `browserSessionFor(run, id)` inside `Effect.acquireRelease(…, { interruptible: true })`. Close it in the release, bounded by `browserSessionClose`, and ignore a failed close. An interrupted step then stops waiting for a browser that never opens, and the runner's Scope closes it later.
- Admin cases open theirs with `openAdminSession` (`e2e/admin-case.ts`), and so do instant navigation's administrator tests through the `administrator` fixture. It keeps the admin failure policy: only a step's own deadline is a timeout, and a timeout inside the step (a Playwright action, the browser, or the preview access probe) fails it, so the case runner reports `failed`, not `timed_out`. A `use` or `evaluate` callback keeps only an `AssertionError`'s message; anything else it throws, a `WorkspaceE2EError` and its diagnostic code included, becomes `<label> failed`, so an admin case annotates no callback-owned diagnostic code. Two styles stay outside the session on purpose: the anonymous instant-navigation tests, which have no case lifecycle, HAR, or seeded data and use Playwright's own `page` fixture, and the devbox agent evals, which launch their own browser for an external harness. When such a test waits for something that may never happen, such as hydration, record the page with `watchPageDiagnostics` (`e2e/page-diagnostics.ts`) before navigating and put `describe()` in the failure, as `temporal-runtime.pw.ts` does: it reports page errors, console errors, watched request outcomes by pathname, and the document state, all redacted.
- The session owns the context lifecycle, the HAR (closed, then sanitized, then handed out), capped console, error, and network capture across every page, bypass priming, and failure classification. `session.primePreviewAccess(url, secret)` exchanges the secret outside Playwright ([preview workflow](preview-workflow.md)); an origin counts as primed once its probe is accepted or when it is not a Workspace deployment origin, and concurrent primes share one probe. Its failures name only the label and `failed`, `timed out`, or `stopped because the browser session closed`; never attach a Playwright cause to a report yourself.
- Failure artifacts go through `session.captureFailureArtifacts(directory)`: it writes the capture logs and the active page's snapshot, sanitized, then closes the session to export the HAR. It has no deadline of its own, so bound the call; checkout bounds it with `artifactCapture`.
- Pass `timeoutMs` only for work Playwright doesn't bound, such as `page.evaluate`; Playwright actions take their own `timeout`.

## Hydration and interaction

- Wait for the specific React handler the component uses before you interact (`e2e/react-handlers.ts`). React props alone don't prove Radix or another composed primitive has installed its handler. Never use network idle as readiness; analytics keeps it open.
- Use Playwright locators and native fill, keyboard, and click, so handlers receive trusted events. Select the control by accessibility role, not a wrapping label. Prefer a stable app-owned ID or form-scoped selector for critical activation.
- Never replace native form submission or link navigation with an evaluated DOM click. An evaluated click can navigate while leaving the driver blocked on the destroyed execution context.
- Detaching any CDP session from a page resets Chromium's virtual authenticator environment there, which removes the passkey authenticator and its credentials. On a page where `holdsVirtualAuthenticator` (`e2e/virtual-authenticator.ts`) is true, leave your own CDP session attached; it ends with the page.
- When a provider page needs an accessibility snapshot, take a fresh Playwright AI snapshot after hydration, resolve its `aria-ref` at once, and never reuse it after the DOM changes.
- Tooltips: wait for the trigger's focus handler, center it in the viewport instantly, let layout settle, and focus it with the browser's native focus command. Assert content through the trigger's `aria-describedby` target. Don't add a `Shift+Tab`/`Tab` round trip, and don't raise the overlay wait to hide a missing interaction.
- Locale switching uses ordinary document links (`switchLocale` in `e2e/cases/locale.ts` activates the hydrated header link, then waits for the URL), not Next.js client-router links, in the full, mobile, and minimal headers alike. Locale is server-owned; cross-locale RSC prefetches and client transitions can fail to commit it.
- Reservation pages render initial prices with the content, so an option change whose price is already loaded never goes back to pending. Wait for pending-then-ready only after a change that issues a new advertised-price request, such as a new date.
- For hosted payment, activate consent and Pay natively once. Arrival at the Nexi page means production has created the attempt and attached the provider session; non-provider outcomes never enter tab management. See [Nexi sandbox](nexi-sandbox.md) for the hosted page.
- After the Nexi redirect, database visibility can still lag. Converge only the retry-safe read for the exact active attempt within the browser-action timeout, and keep a fixed diagnostic for the last observed state. Reject malformed provider-session responses at the checked-in OpenAPI contract and never retry payment creation after a decode failure.

## Preparation before a state-creating action

Keep UI- or provider-backed preparation apart from the native activation that creates state:

1. Start side-effect-free preparation in a short Playwright evaluation that returns at once and keeps a bounded status in the page. The reservation form does this with `prepareReservationForm({ detachInto, preparation })` and reads the status with `readReservationPreparationState`.
2. Poll that status under the existing semantic timeout. Keep preparation errors.
3. Focus the hydrated form-scoped submit control and activate it with a separate native keyboard command.
4. Poll the destination URL.

A preparation script may press the existing advertised-price retry control when that error is rendered. That retry is read-only and doesn't reset the preparation deadline.

The reservation-preparation UI action (`e2e/checkout/payment.ts`) may retry once after its recognized generic error, but only with the same `checkoutAttemptId` in the same `checkoutSessionId`; the backend attempt key is the idempotency boundary. Never extend that retry to payment creation, and don't raise timeouts to hide a browser transport limit.

## Streamed pages

- After a full load, `/account` streams its layout and content in separate Suspense boundaries, and React can delay revealing content by a few hundred milliseconds. Clicking a section before its content hydrates makes React render a second panel beside the hidden server copy, and strict locators such as `#account-profile-form` fail. Section selection waits for the target panel's always-rendered anchor to carry React props before the native click. Legal has no anchor because it renders only when active.
- Never wait on an element handle pinned before a streamed reveal. React's `$RC` swap can land after `load`, and the loading shell's disabled section buttons share the real buttons' accessible names. `waitForReactClickHandler` resolves its locator again when the observed node leaves the document.
- Profile navigation failures never attach the Playwright cause, which can hold private profile values. They keep the closed diagnostic code and name only the stage and failure kind (`timeout`, `strict-mode-violation`, `error`).

## Review screenshots

Review screenshots are PR-review artifacts, not test evidence. General account captures run only when `WORKSPACE_E2E_REVIEW_SCREENSHOTS=true`, decoded once by `reviewScreenshotsEnabled` in `e2e/e2e-env.ts`; the campaign composer has its own `WORKSPACE_E2E_CAMPAIGN_REVIEW_SCREENSHOTS=true` opt-in, so manual campaign evidence does not enable unrelated account captures. The administration captures include both Overview locales and a customer calendar rendered for a run-scoped synthetic Dotypos profile; the profile is expired in `finally`, and customer links are masked in Overview captures. CI uploads `e2e-artifacts/account-review/*.png` as `workspace-account-review-<run>-<attempt>`.
