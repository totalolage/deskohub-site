# Adding a locale

Workspace paths are relative to `apps/deskohub-workspace`. The locale is added when every step below is done and these pass: the Workspace typecheck and full test suite, and the tests of every package the steps change (`bun turbo test --filter=@deskohub/i18n --filter=@deskohub/nexi --filter=@deskohub/workspace-customer-api --filter=@deskohub/workspace-admin-api` at least, golden contracts included).

1. **Registry.** Add the entry to `packages/i18n/src/locale-registry.ts` with every field ([architecture](architecture.md#the-locale-registry)). Give it a `fallbackChain` that reaches `cs-CZ`. Update the expectations in `locale-registry.test.ts`.
2. **Inlang settings.** Add the tag to `locales` in both Workspace projects, `project.inlang/settings.json` and `features/administration/i18n/project.inlang/settings.json`, in registry order. The two `inlang-project.test.ts` drift tests fail until both match. The mobile app's project follows in step 13.
3. **Glossary.** Add `references/glossary/<locale>.md` to this skill, covering every term ID in [terms.md](glossary/terms.md), and add the locale to the register (§2) and plural (§8) sections of [style-guide.md](glossary/style-guide.md). Translation starts after this.
4. **Catalogs.** Add `features/i18n/messages/<locale>.json` and `<locale>.json` in every area folder under `features/administration/i18n/messages/`, translated per [translation-workflow.md](translation-workflow.md) and parity-checked against `cs-CZ`. Compile both projects ([catalogs](catalogs.md#compiling)). When translation runs in a separate change, the structural change ships placeholder catalogs first: the `en-US` text with plural match keys narrowed to the locale's CLDR categories, and the `cs-CZ` value for any key whose English structure differs from the Czech one, so the parity check passes before translation starts. The administration `email-campaigns` catalog names each language in message families such as `emailCampaignsComposerHiddenContent<Language>` (one member per locale, alphabetical by English name), which typecheck-complete maps read: add the new language's member to every locale's catalog. Messages that name which languages fall back to English or Czech must not list languages, since every new locale would make the list stale.
5. **Typecheck.** Run the Workspace typecheck and fill every per-locale map it names. Maps built with `mapSupportedLocales` or keyed by `Locale` or `SupportedLocale` turn a new locale into a type error until they have a value.
6. **Vercel headers.** Add the tag to the locale alternation in the `vercel.json` header route for locale pages. `vercel.test.ts` checks it against the registry order.
7. **Database.** The locale `CHECK` constraints come from the customer Inlang `locales`, so step 2 changes the schema. Generate the migration with `bun turbo db:generate --filter=deskohub-workspace`; `db/migrations/*_supported_locales_de_uk_sk/` shows the shape (one `CHECK` per locale column). Follow the migration folder-name rules in the `deskohub-repository` development reference.
8. **API contracts.** `CustomerLocale` and `AdministrationCampaignLocale` gain the tag, so the customer OpenAPI and administration wire-contract golden fixtures change. Regenerate them as their tests describe and review the diff for shipped clients.
9. **Legal documents.** Add `features/legal/locales/<locale>/` with `documents.tsx` (exporting `translation`: the documents and the notice that the Czech version governs) and `summaries.ts`, and register the locale in `features/legal/content.tsx`. Each document's `updatedAt` is the document date as `Intl.DateTimeFormat` prints it in the locale's long form (`features/public-pages/public-page-definitions.test.ts` checks it), placeholder documents included. Add `translation-date.ts` beside `documents.tsx` and list it in `features/legal/legal-translation-dates.ts` (typed to require every locale except the governing Czech one). Move that date forward whenever the locale's legal text changes while the Czech version stays the same; the legal pages' sitemap `lastmod` uses the later of it and the document date, and the pages keep showing the document date. Record the new published versions in `features/legal/document-version.test.ts` and in `consentBannerDocumentVersions` (`features/legal/consent-banner-revision.ts`). Recording them changes the banner revision, which reopens the cookie banner once for every visitor.
10. **Fonts.** A `latin` locale whose letters the brand face (Sculpin) covers needs nothing. Any other `script` gets its typography from `apps/deskohub-workspace/features/i18n/locale-fonts.ts`, which the locale layout applies to `<html>` as `--font-text`, the stack the heading, subheading and body font tokens read:
    - a companion face, limited by `unicode-range` to a script the brand face lacks, between the brand face and its metric-matched fallback (Cyrillic: Montserrat; Devanagari: Poppins, then the system Devanagari fonts);
    - a text face that sets the whole page ahead of the brand face, where mixing faces letter by letter would show (Vietnamese, script `latin-vietnamese`: Montserrat). The brand wordmark keeps Sculpin through the `font-wordmark` token;
    - A script with marks above and below the line, or whose letters join, also needs its line metrics set by language in `app/globals.css`, as `:lang(hi)` does for Devanagari: Tailwind's `--text-*--line-height` and `--leading-*` tokens and any arbitrary `leading-[…]` raised to 1.6–1.75, and letter spacing reset, since most tracking utilities are arbitrary values. The `font-wordmark` elements keep their own metrics.
    Add the face files under `assets/fonts/<Family>/` with the family's `OFL.txt`, subset to the Google Fonts `unicode-range` slices the script needs, and never preloaded, since only pages of that script use them. Add the script's `scriptTypography` entry; `locale-fonts.test.ts` and `app/[locale]/layout.test.ts` pin the stacks. Check the result with real text in the script at phone and desktop width.
    - a language name face: every page names every language in itself (the header language menu, the footer language links, the profile language select), so the new language's `nativeName` needs its script's face on other locales' pages too. Each script outside `latin` has an entry in `languageNameFaces` (`locale-fonts.ts`): a face that holds only the letters of the registry's native names in that script, which the layout names on every page as `--font-language-name-<tag>` and `languageNameStyle` (`features/i18n/language-labels.ts`) applies to the name. Cut it from the script's face with fontTools, passing every native name in the script, and do the same when a native name changes, for example `pyftsubset assets/fonts/Montserrat/cyrillic.woff2 --text="Українська" --layout-features='*' --no-ignore-missing-unicodes --flavor=woff2 --output-file=assets/fonts/Montserrat/language-name-cyrillic.woff2` (one file per static weight, as for Poppins 400 and 600). `language-name-fonts.browser-acceptance.test.ts` fails when a name has a letter its face lacks.
11. **Hand-listed tests.** Update tests that enumerate locales themselves (sitemap, hreflang alternates, structured data, public page metadata, the locale switcher and footer language list, request-locale and proxy tests, the consent-banner versions in `features/legal/consent-banner-revision.ts`, and others the suite reports).
12. **E2E smoke.** Add the locale to `localeSmokeLocales` and `localeSmokePlans` in `e2e/cases/locale-smoke.ts` (its Accept-Language values and the locale its language menu switches to, keeping the switches one cycle through every smoke locale), and its case ID `locale-smoke-<tag in lowercase>` to `e2e/playwright-checkout/case-catalog.ts` and the signed-out cases in `e2e/checkout/booker.ts`.
13. **Mobile app.** The app serves exactly the registry's locales, so a new locale is added there in the same change. Under `apps/deskohub-mobile`, add the tag to `locales` in `project.inlang/settings.json` in registry order, add `messages/<locale>.json` with the base catalog's keys in its order, and compile. `AppLocale` is the type Paraglide generates from that project, and device languages resolve through the registry's `matchSupportedLocale`, so there is no hand-written locale list or language map to update. Then run the app's typecheck and tests: maps built with `mapSupportedLocales` must gain a value, and any `script` other than `latin` gets the system font in place of the Latin-only brand face (`src/ui/text-style.ts`); the app bundles no companion fonts, and its type styles set no line height, so the system font's own metrics leave room for marks above and below the line. See `deskohub-mobile`.

Nothing changes in Dotypos. Staff-facing text, such as Dotypos reservation notes and staff notifications, stays Czech for every locale. Operator-authored content (campaign and automation emails, discount labels) needs no new fields: recipients in the new locale get it through the locale's fallback chain ([architecture](architecture.md#content-that-falls-back-through-the-chain)).
