# Administration localization

The administration serves `en-US` and `cs-CZ` under the locale segment: `app/[locale]/admin` answers `/<locale>/admin/...`. It follows the customer locale chain (saved preference, URL, cookie, Accept-Language, default) and has the same language switcher, which saves a signed-in customer account's preference.

## Routes and the proxy

- `proxy.ts` treats every path whose first or second decoded segment is `admin` as administration, however it's spelled. A page load (`GET` or `HEAD`, including router requests) without a Better Auth session cookie goes to `/<locale>/auth/sign-in?returnTo=<path>`. With a cookie, the proxy reads the session and the grant (`readAdministrationRequestAccess`): a stale session goes to sign-in, an account without the grant is rewritten to the ordinary customer 404 page, and a failed read answers 503. Pages stream behind the static admin shell, so only the proxy can still set the status and keep the shell from non-administrators; the page and action guards check again (see [dashboard.md](dashboard.md)). Server Actions pass straight through to their guard. Otherwise an unprefixed `/admin/...` URL redirects to the resolved locale and keeps its query, so bookmarks, emailed links, and the `dhw auth` URL keep working. Every administration response is `private, no-store` and varies on `Cookie`.
- Customer providers (GTM, PostHog, cookie consent, referral remembrance, unsaved-changes guard) live in `app/[locale]/(site)/layout.tsx`. The administration sits beside `(site)` and gets only the root `<html>`, so it never loads them. Put new customer routes inside `(site)`. Each side has its own `error.tsx` and `not-found.tsx` (`(site)/` with customer copy, `admin/` with shell copy), so a fallback renders inside its own layout; a boundary at `[locale]` would replace the whole `(site)` subtree and drop the customer providers. `admin/[...catchAll]` keeps unknown administration paths out of the customer catch-all; it must share the `@modal/[...catchAll]` parameter name, or Next rejects the routes as ambiguous.

## Paths in code

- Write administration paths unprefixed (`/admin/reservations/${id}`). `AdministrationLink` and `AdministrationRecordLink` add the route locale themselves.
- For any other in-app use, place the path with `localizeAdministrationHref(path, locale)` (`features/administration/administration-href.ts`): form `action`s, `router.push`, plain `<a>` to route handlers such as the invoice PDF. Client components take `locale` from `useRouteLocale()`, server components from `getRequestLocale()`, and Server Actions from `resolveActionLocale()`.
- `useRouteLocale()` (`features/i18n/route-locale.tsx`) reads the locale the root layout provides. Don't read it from `useParams()` or `usePathname()`: on a dynamic route those are request data, and a client component reading them outside Suspense fails the prerender. The compile-only build check doesn't prerender, so only a full build (the Vercel preview) catches it.
- Revalidate an administration page with `revalidateLocalizedPath(path)` (`features/i18n/server/revalidate-localized-path.ts`). A mutation doesn't know which locale's copy is cached, so it revalidates both.
- Keep a URL unprefixed when it leaves the app, such as the `dhw auth` approval URL or a link in the administration API contract. The proxy opens it in the operator's language.
- Administration pages and layouts stay synchronous (`no-blocking-administration-routes`). A synchronous page that only redirects may redirect to the unprefixed path and let the proxy place it.
- A page frame with copy (the sr-only `<h1>`, toolbar labels, Suspense fallback labels) can't read the locale in the synchronous default export. Render a feature-level async screen component named for the screen, such as `DiscountCodesAdministrationScreen`, whose only top-level await is `getRequestLocale()`. That reads `next/root-params`, which the prerender knows, so the frame stays in the instant shell. The screen renders the frame and the Suspense boundaries and passes `locale` to the async data children. Don't await anything else before the frame. Component tests that render such a screen mock `next/root-params`, as `app/[locale]/admin/reservations/page.test.tsx` does.

## Actions and errors

- A Workspace action's context already carries `locale` from the locale middleware, so build action copy with it. In an `Effect.fn` action, type the generator's second parameter as `WorkspaceActionContext<typeof schema>` so the pipe step `(effect, _input, { locale })` type-checks.
- The administration API and `dhw` forward application error messages, so those stay English. Give the tagged error a structured field (a `reason` union, the resource kind) and map it to administration copy in a module beside the action, such as `features/discounts/admin/mutation-error-message.ts`. A `"use server"` file can export only async functions. Never forward `error.message` to the Admin UI.
- The same applies to display fallbacks that the API also returns, such as "Unnamed customer": the service keeps the English text in `displayName` and adds a structured signal beside it (`hasName`), which the contract doesn't declare. Services share the shape and the English text from `features/administration/customer-name.ts` (`AdministrationCustomerName`, `unnamedCustomerDisplayName`). The screen renders the area's catalog fallback when the signal says so, through one helper per area (`getAdministrationCustomerName`, `formatDiscountAdminCustomerName`, `getInvoiceCustomerName`). Don't compare the English text.
- A form schema with copy becomes a `(locale) => Schema` factory. Name a tracked action for what it does (`setCustomerDiscountGroup`), never after its translated button label.
- Format date-times on the server and pass the text into client tables (see the hydration note in `deskohub-react-ui`).

## Messages

Administration copy has its own Inlang project, `features/administration/i18n/project.inlang`, compiled by `i18n:compile:administration` (which `i18n:compile` depends on) into the ignored `features/administration/i18n/paraglide`. Import it as `m` from `@/features/administration/i18n`, never from `@/features/i18n`, and pass `{ locale }` at each call, as customer copy does. Customer-facing content inside the administration, such as email previews or product names, keeps the customer `m`. Both projects compile as locale modules; see Workspace builds in the `deskohub-repository` development reference.

Only a separate project keeps this copy out of customer bundles. Every client-used customer message lands in one chunk that all routes load, and administration messages compiled into the customer project leaked into it through `m`, a separate barrel, Turbopack clusters, and with chunk merging off. A single customer import of one administration message pulls the whole administration catalog into customer chunks.

### Catalogs

- Each area has its own catalog pair, `messages/<area>/{en-US,cs-CZ}.json`, named after the feature directory that owns the screens: `shell` (`admin-shell.tsx`, breadcrumbs, switcher), `administration` (overview, reservations, customers, bookings, orders, operations), `discounts` (codes, vouchers, sales, customer codes), `accounting` (invoices), `access-codes`, `email-campaigns` (campaigns, audiences), `admin-cli` (CLI sessions and approval), and `administrators` (`features/administrators/admin`, the administrator roster). Parallel work on different areas then never edits the same file.
- Prefix every key with its area in camelCase (`administrationReservationListTitle`, `discountsCodeFormSubmit`, `emailCampaignsSendConfirm`). Keys must be unique across all catalogs. Don't put shared words in a common catalog; each area owns its own copy even when the words repeat.
- A new area adds its folder and a `pathPattern` entry in `project.inlang/settings.json`.
- Write full sentences in both locales. Czech copy follows the customer catalog (`features/i18n/messages/cs-CZ.json`) for terms such as rezervace, poukaz, faktura, and přístupový kód; operator copy addresses the reader formally (vy).

### Shared primitives and formatting

- Shared primitives in `features/administration` never build copy from nouns. Screens pass complete localized strings: `AdministrationTableToolbar` `label`, `AdministrationTableCount` `label` (the count with its noun), and the `label` of labelled loaders. Primitives with fixed copy read the route locale themselves. Examples are the route, modal, breadcrumb and filter loaders, `ConfirmDialog`, the table's actions header, `Pagination`, and `NexiOrderLink`.
- Format dates, times and money with `features/administration/formatters.ts`, passing the route locale: `formatAdministrationDateTime(value, locale)`, `formatAdministrationPlainDate`, `formatAdministrationReservationDate`, and `formatAdministrationMoney` (built on `@deskohub/i18n/currency`). Date-times use the 24-hour clock in both locales. Operators work on Prague time. A day period would also make the client tables fail hydration. Depending on its ICU version, Node separates "PM" with a narrow no-break space, and in ranges it always does. Chromium writes a plain space. Don't add per-screen `Intl` formatters. Format any range or other time format on the server.
- Write counts as Inlang plural variants, as the customer catalog does: declarations `input count` and `local countPlural = count: plural`, with `one` and `other` in English and `one`, `few` and `other` in Czech. Don't pick the noun in code. Group a count's digits for the locale: inside a message with Inlang's `number` function, outside one with `formatCount` (`shared/utils/number.ts`). `AdministrationTableCount` formats its `count` itself, so pass the raw number.
- The administration API and `dhw` share the services with the Admin UI, and their output stays English. Leave English display fields the API contract exposes (`typeLabel`, status `label`, timeline `title`) unchanged. Add a stable code beside each one (product, status code, timeline `event`) and render the copy from the code in the UI. The contract's encoder drops fields it doesn't declare. Map typed service errors to catalog messages at the Server Action with the action's locale. Don't localize inside services.
- Product names inside the administration are customer content. Render them from the customer catalog with the route locale, through `features/administration/reservation-product.ts`.

## Build-output check

`features/administration/i18n/administration-messages.build.test.ts` reads a production build. It fails if any administration message text appears in a chunk a customer route loads, and also if administration chunks contain no administration text in either locale or customer chunks no customer text, so a broken build or matcher can't pass. It matches message text, not names, because Turbopack renames modules. It guards multi-word or 12-character texts that the customer catalog doesn't share. Shorter single words could be coincidental literals. A text of three or more words counts on its own, so copy pasted into a customer component in one language fails the check. Shorter phrases can be coincidental too (a validation library's `"at least"`, a schema's `description:"Reservation status"`), so they count only when the chunk also holds a text of the same message in every other locale. Each message's function calls every locale's implementation, so an imported message always brings all its locales along. A message that reads the same in every locale, or whose other locales have nothing longer than two characters, counts on its own text. A text the administration API contract (`packages/workspace-admin-api/src`) also declares, such as an audience label `dhw` shows in English, needs the message's translations alongside, because the contract ships wherever its schemas do. The message's other texts, such as its Czech translation or another plural variant, follow the usual rule. Paraglide compiles a message with placeholders into a template literal split around each input, so such a message is matched by its distinctive static runs, anywhere in the chunk. Matching decodes `\xNN` and `\uNNNN` escapes first, because the minifier writes Czech letters such as `ú` as `\xfa`.

The guard scans every emitted script under `.next/static`, not only the ones route manifests list. A chunk counts as administration-only when administration route manifests list it or another chunk loads it lazily by file name, and no customer-reachable chunk loads it. Customer route chunks, `rootMainFiles`, and chunks nothing accounts for are customer-reachable, as is everything they load. The pure logic lives in `administration-message-leaks.test-utils.ts`, with unit tests in the default suite.

The `*.build.test.ts` pattern is excluded from the Workspace `test` script and runs by path:

```bash
bun turbo run build:compile --filter=deskohub-workspace
bun --cwd apps/deskohub-workspace run test:build-output
```

Compile mode writes every client chunk without prerendering and needs no environment. CI runs the same steps in the `validate-administration-messages` job, which `test-functional` requires. A failure names the text, chunk, and customer routes. Find the customer client module that imports `@/features/administration/i18n` (directly or through a shared component) and move the copy or the component back into the administration.
