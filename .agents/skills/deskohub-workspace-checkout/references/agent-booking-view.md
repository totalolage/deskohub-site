# Agent booking view (MCP Apps)

The customer MCP server (`app/api/mcp/route.ts`) serves an MCP Apps view, `ui://dh-workspace/booking-v2.html`, that hosts such as ChatGPT, Claude, and VS Code render beside the conversation. `show_booking` is the only tool linked to it. Paths below are relative to `apps/deskohub-workspace/features/agent-tools/`.

## Tool metadata and resources

- `agent-tool-mcp-handler.ts` publishes every tool's access in `_meta["cz.deskohub.workspace/access"]` (`agent-tool-metadata.ts`). `tools/list` answers every client with the public and the signed-in tools alike, so a client without a token selects by this key. Administration tools (`administration`) are listed only to an administrator's agent; see the administration skill's `references/dhw-cli.md`, "MCP tools". WebMCP registers only tools that are `public` and link no view (`isSiteTool` in `webmcp/agent-tool-mcp-client.ts`). Keep the selection on published metadata, not on a list of names.
- A tool links a view by setting `view` in `defineAgentTool`. The handler registers each distinct view as a resource, with `_meta.ui` on both the registration and the `resources/read` content, and links the tool under `ui.resourceUri`, the flat `ui/resourceUri`, and `openai/outputTemplate` (`agent-tool-view.ts`). The server is stateless and can't see 2025-era client capabilities, so it always registers and links. Every result therefore stays complete as `structuredContent` and as JSON text.
- Page links in tool results (`reservation_url`, `status_url`) are locale-agnostic; `pay_url` keeps its locale. See the page URL rule in `deskohub-react-ui`.
- `llms.txt` describes the published customer tools and the booking guidance (`customerAgentCatalog.published`, which never holds an administration tool and gives the guidance a client admitting checkout is given) by access, and the WebMCP site tools by `registersAsSiteTool`, the rule `isSiteTool` applies to `tools/list` (`agent-interfaces-markdown.ts`). It describes the site tools while `webmcp_site_tools` isn't off for every visitor (`SiteToolsFeatureFlagService.release`).
- The view declares no connect or resource domains, and only the site origin as ChatGPT's `redirect_domains`. ChatGPT's directory requires a widget domain, so the site origin goes in `openai/widgetDomain` for every client and in `ui.domain` only for ChatGPT: Claude accepts only its own `{hash}.claudemcpcontent.com` form there. `openai/widgetDescription` and `show_booking`'s `openai/toolInvocation/*` status (64 characters at most) come from the `AgentToolView`. A breaking change to the document or to the `show_booking` result publishes a new versioned URI.

## Directory clients

ChatGPT and the Claude apps list the server in their app directories. `identifyAgentToolClient` (`agent-tool-client.ts`) names each request's client from the `clientInfo` it carries (`initialize`, or the 2026-07-28 `_meta` envelope; `openai-mcp`, `Anthropic/ClaudeAI`) and otherwise from the User-Agent (`openai-mcp/…`, `Claude-User`); anything else is `other`. Every client sees every customer tool. The route reads the request's JSON-RPC messages once (`readMcpRequest`, `agent-tool-mcp-messages.ts`) for both the identification and the handler's authorization, and passes the client to `customerAgentCatalog.forClient` (`customer-agent-catalog.ts`), the one place that knows which customer tools a client gets, in what order, and the server instructions for them, and to the handler for the view's `_meta`. The handler serves the tools and instructions it is given and knows no customer tool names. ChatGPT's directory admits commerce only for physical goods (`admitsCheckout`, private to the catalog), so its `start_reservation` is `startReservationOnWebsiteTool`: a public, read-only tool with the same name and arguments that books nothing and returns the prefilled reservation page link that `get_quote` returns. Its `noauth` scheme and annotations follow from the tool definition. `get_reservation_status` and `list_my_reservations` stay signed-in tools for ChatGPT. Nothing ChatGPT reads mentions paying, Pay links, or holds: keep the instructions, tool, resource, and input-schema descriptions, and public tools' output schemas free of them, and put payment copy only where `admitsCheckout` holds. The catalog builds each instruction sentence from the tools the client is listed and from `admitsCheckout`, and `llms.txt` takes its guidance from the same listing; `customer-agent-catalog.test.ts` checks structure (a tool is named only when listed, nothing about paying for ChatGPT), not wording. Signed-in tools' results report the customer's own orders, payment state included. Tools served beside the customer tools, such as administration tools, are appended after the catalog's tools and get no per-client change; the instructions mention a customer tool only when the client sees it. Claude Code reaching us through Anthropic's gateway on a 2025-era protocol shares `Claude-User` without `clientInfo`, so it is served as a Claude app.

## Booking mode

The handler gives each call `CallableAgentTools`: the published tools its caller may call, meaning the public tools plus the signed-in tools its token's scopes grant (`isAgentToolGranted`). `show_booking` answers `booking_mode: "reserve"` only when that set holds `start_reservation`, which depends on the caller's token: the set holds it when the token grants `reservations:create`. ChatGPT's public `start_reservation` is always in it, so the mode also needs the directory to admit checkout: the catalog lists `makeShowBookingTool({ admitsCheckout })` (`show-booking.tool.ts`) per client. Otherwise the mode is `reservation_page`. The mode travels in `structuredContent`, so the model reads the same fact the view does.

For a review account, `start_reservation` returns a simulated hold whose `pay_url` opens the payment-disabled page, and `list_my_reservations`/`get_reservation_status` report its samples and holds (lifecycle reference, review account sandbox).

The view sends `start_reservation` only the quoted selection, `locale`, and `early_setup: true` when the customer chose it, never `marketing_consent`. A meeting room's early-setup choice appears after the check in `reserve` mode only. It's enabled only when `check_availability` reports `meeting_room.early_setup_available`, which comes from the reservation page's start-times listing (`findMeetingRoomStartTime`). Later checks that still report setup free keep the choice. Like the reservation form, a completed check that reports it taken unchecks it; running, failed, or cleared checks leave it. When the call fails, the view shows its own message for the error code and the prefilled reservation-page link from `get_quote`.

In `reservation_page` mode the view starts no booking and never shows the Pay link or payment wording, which ChatGPT's directory requires. Keep that mode's copy (`bookingWidgetReservationPageHint`, `agentToolBookingViewReservationPageNote`) payment-neutral.

## View code (`booking-widget/`)

- `booking-draft.ts` holds the pure state: locale choice, prefill, the required Reserved Desk workstation, and `makeBookingDraftSchema`, an Effect Schema union keyed by `family` that validates only the chosen family's fields, with messages in the view's locale, and decodes them to tool arguments. `booking-form.tsx` keeps the selection in React Hook Form with `effectSchemaResolver`; the Check button calls `handleSubmit` from its click, and switching the family or duration clears field errors. `booking-host.ts` is the `BookingHost` service over ext-apps `App`, and `booking-atoms.ts` runs its Effects through an Effect Atom runtime. The view has no `Effect.run*` and no `@deskohub/next-effect`, which would bundle `next/navigation`.
- Every tool call goes through the host's `tools/call` (`app.callServerTool`). `/api/mcp` rejects the sandbox's foreign origin. Results decode with the tools' own `*.schema.ts` result schemas plus `agentToolErrorResultSchema`. Keep those schema modules browser-safe: no server imports.
- Tool `note` fields and error `message`s are written for the agent. The view renders only its own catalog copy, in the site's informal Czech ("ty"): facts such as prices, the discount, and the expiry come from the results, and errors are worded from their `code`.
- Locale order: the agent's `locale` argument, then `hostContext.locale`, then ChatGPT's `window.openai.locale` (any `cs*` gives `cs-CZ`), then `en-US`. `BookingHost.locale` resolves it once the tool input or result arrives, apart from `start`, so loading and startup failures use it too. A view whose locale differs from the result's lists the offerings again in its own locale. Copy comes from the customer Inlang catalogs, called with `{ locale }`.
- Hosts sandbox the view without `allow-forms`: the browser blocks a form submission before its submit event fires, so actions are `type="button"` clicks.
- Links: with `openLinks`, `app.openLink`; otherwise ChatGPT's `window.openai.openExternal`; otherwise the browser follows the plain anchor. The address always stays visible as text.
- Theme: `BookingHost` applies the host context's `theme` and `styles.variables` with ext-apps `applyDocumentTheme` and `applyHostStyleVariables`, on connect and on every `onhostcontextchanged`. It skips the host's font CSS (`applyHostFonts`): the sandbox admits no resource domains. When the context has no theme, ChatGPT's `window.openai.theme` gives it, followed on `openai:set_globals`; with neither, the view stays light. `booking-widget.css` points the brand tokens at the host variables (`--color-text-primary`, `--color-text-secondary`, `--color-background-primary`, `--color-text-danger`, `--color-ring-primary`, `--font-sans`), with brand fallbacks for light and `[data-theme="dark"]`. Keep colours in that file, not in components: use the `bg-surface` and `text-muted` utilities, and give shared primitives a tone that tints the text colour, never `bg-white`. Hosts expose no accent colour, so the brand orange stays. No orange keeps both 4.5:1 for white text on it and 3:1 against a dark host's background, so in dark mode the accent turns light (`#f08a4b`) and `--color-white`, the primitives' text on the accent, turns dark. Focus rings use the host's ring colour. Check WCAG AA contrast in both themes when you change a colour.

## Build

`booking-widget:build` (`build-booking-widget.ts`) runs `Bun.build` with `compile: true` on `index.html`. The output is one self-contained document in the gitignored `booking-widget/generated/`, with Tailwind applied by a CSS `onLoad` plugin over the shared `shared/styles/brand-theme.css`, and React's production build. `show-booking.tool.ts` imports it with `with { type: "text" }` (typed in `types/booking-widget-html.d.ts`). `build:compile`, `dev`, `test`, and `lint:knip` depend on the task; `typecheck` doesn't need the file. `dev:booking-widget` rebuilds on change. The document is about 755 KB (about 222 KB gzip). React Hook Form with the resolver and the shared form primitives adds about 15 KB of that gzip size. Of the rest, react-dom takes about 66 KB; the MCP client protocol and zod that ext-apps brings about 65 KB, as module-level schema calls no bundler can drop; Effect Schema decoding about 30 KB and Effect Atom about 10 KB; tailwind-merge (through the shared primitives' `cn`) about 9 KB; the CSS about 6 KB. Measure with `Bun.build({ metafile: true })` on `booking-widget.tsx`.

## Tests

- `booking-draft.test.ts` and `booking-form.test.tsx` (happy-dom) cover the state, the validation through the resolver, and the rendered results. React DOM only handles `input` events when it loads after happy-dom registers, so `booking-form.test.tsx` registers the DOM at module level and imports Testing Library and the form dynamically. `show-booking.tool.test.ts` covers the mode, and `customer-agent-catalog.test.ts` which client's view may start a booking. The route tests cover the resources, the metadata, and both modes with real tokens. `agent-tool-mcp-handler.test.ts` covers `CallableAgentTools` by token scope.
- `booking-widget.browser-acceptance.test.ts` builds the real document and renders it in a `sandbox="allow-scripts"` iframe. The host is an ext-apps `AppBridge` with a null client, in `booking-widget.browser-harness.ts`, and its `oncalltool` and `onopenlink` are stubbed through Playwright `exposeFunction`. The harness takes the host's locale, theme, and style variables, and `window.changeBookingHost` changes them mid-session. Cases cover a host without `openLinks` that injects ChatGPT's `window.openai` (an init script in the frame, which can also carry its theme and locale) and a host with neither. ChatGPT's reservation-page mode runs in both themes and both locales. Set `BOOKING_WIDGET_SCREENSHOT_DIRECTORY` to save a screenshot of each state for PR evidence.
- `e2e/cases/agent-booking.ts` checks the signed-in agent's `reserve` mode and reads the linked view.
