# Email campaigns

Admin email campaigns live in `apps/deskohub-workspace/features/email-campaigns/`. The body document, templates, rendering, and content hash are under `body/`. The domain core (schema, audiences, recipient resolution, services) is in the rest of the feature, with tables in `db/schema/email-campaigns.ts`.

## Glossary

- **Campaign**: one email an admin composes and sends once. Its status moves Draft → Sending → Sent; a Failed send retries only undelivered recipients. Only a Draft can change or be deleted. **Duplicate** copies any campaign into a new Draft; an automated copy's flow must pass the rules a save applies (`validateStoredAutomationFlow`), so a legacy flow that breaks one fails with that rule's error instead of being copied.
- **Delivery**: `once` (above) or `automated` (statuses Draft, Active, Paused, Archived). Every one-off operation (edit, delete, test send, code issue and confirmation, send, retry) checks `delivery = 'once'` inside the shared service, not the adapters, and refuses an automated campaign with `CampaignDeliveryMismatch` (`campaign-delivery-mismatch`; `dhw` gets a 409).
- **Purpose**: `marketing` or `operational`. Marketing campaigns reach only customers with active marketing consent (legal's `marketingConsentState`, used inside the audience and delivery queries) and carry unsubscribe links. Operational campaigns skip consent and carry a reason line: fixed localized copy unless the locale content sets `operationalReason` (trimmed, non-empty; part of the content hash).
- **Template**: a code-defined React Email layout the campaign selects by key. Admins can't edit templates.
- **Audience**: a saved, named filter tree (`AudienceFilter`): nested AND/OR groups of attribute conditions. Drafts follow the audience live. An audience a Draft uses can be archived but not deleted. Unrelated to discount-code audiences.
- **Attribute catalogue**: `audienceAttributeCatalogue` in `@deskohub/workspace-admin-api` (`audience-filter.ts`) lists every customer attribute an audience can filter on. Each entry comes from its kind's constructor (`countAttribute`, `dateAttribute`, `setAttribute`, `booleanAttribute` in `audience-attribute-kinds.ts`) and declares its wire shape, choice params and period in wire order, whether it takes a reservation product filter, its English `label` (for `dhw` and the API schema description), its Admin UI section and defaults, its choice options and controls, and for sets its value source and whether it narrows locales. Its English editor and summary wording predates the bilingual Admin UI, which no longer reads it. Dropping those fields changes the shared contract and so needs a `dhw` release (see `deskohub-workspace-administration/references/dhw-cli.md`); do it alongside the next real `dhw` change. A condition is `{attribute, _tag: "Condition", params?, operator, value?}`, `attribute` first.
  - Adding an attribute means one catalogue entry, its resolver in `audienceAttributeResolvers` (`features/email-campaigns/backend/audience-attribute-resolvers.ts`), and its Admin UI wording in `features/email-campaigns/admin/audiences/audience-attribute-wording.ts` with `emailCampaignsAudience*` messages in both locales of the `email-campaigns` administration catalog. The resolver and wording types fail the typecheck when an entry has none. Reservation product families and properties are worded in `admin/audiences/reservation-product-wording.ts`. The schema, builder, defaults, menu, summary, fact requests, evaluation, and locale narrowing dispatch on the kind (`viewAudienceCondition`), reading the entry for structure and the wording for words; don't add per-attribute switches elsewhere. `audience-attribute-extension.typecheck.ts` and its test show a new count attribute with test-local wording.
  - Counts reject `< 0` (nobody) and `≥ 0` (everyone) on the operator. Summaries say "no" only for `= 0` and `< 1`, "any" only for `> 0` and `≥ 1`, and read other comparisons literally.
  - **Count**: `reservationCount` (params: `dateBasis` visit or booking, `period`, optional `status`) and `campaignEmailCount` (params: `purpose` marketing, operational or any, `period`, optional `campaign`). Operators `eq ne lt lte gt gte` against a whole number ≥ 0. `campaign` (`campaignSourceParam`, part `campaign`) is `Specific` (one campaign) or `This` (the evaluating automation's campaign); absent means any campaign, so older filters keep their bytes. With a campaign the purpose must be `any`.
  - **Date**: `firstVisit`, `lastVisit` and `accountCreated`. Operators `in` a period, `notIn` (a value exists outside it), and `none` (no value: never visited, no account).
  - **Set**: `locale`, `dotyposTags` (also `allOf`), `discountGroup`. Operators `anyOf` and `noneOf`.
  - **Boolean**: `hasAccount`, operator `is`.
- **Product filter** (`ReservationProductFilter`): `reservationCount.params.product` and `lastVisit.params.product` limit those attributes to one reservation family and, optionally, to property conditions on it (enum any of / none of, boolean is, number compared like a count). The contract keeps it structural; Workspace's `audienceFilterSchema` checks each property, operator, and value against `reservationProductFamilies` (`features/reservation/reservation-product-descriptor.ts`), the single source for families, properties, values, and catalog names. Evaluation is SQL on `workspace_reservations.reservation_details` through the `StoredReservationDetails` accessors (`reservation-product-condition.ts`); a snapshot missing a property's field, or holding it in another JSON type, matches only family-level conditions.
- **Date period** (`DatePeriod`): every dated condition uses it. Any time; any time so far (`Past`, through the evaluation time); the last N days/weeks/months/years; from D1 to D2; since D (through the evaluation time); from D onward (future included); until D; within N units before or after the trigger (`TriggerWindow`, automation conditions only; without a trigger the evaluation time stands in). Days are Prague calendar days. "Last N units" subtracts N units from the evaluation time on the Prague calendar (`datePeriodBounds`), so a month keeps its length across DST. Periods that run to the evaluation time include it (`startsAtOrBefore`); calendar-day ends stop before the next Prague midnight (`startsBefore`). Dotypos range filters only have a strict end, so an inclusive end queries 1 ms later. The evaluation time is the send time for a real send. Summaries and the builder name periods with `describeDatePeriod`.
- **Send**: the one record that freezes a campaign's recipients and snapshots the audience filter it used (`email_campaign_sends`).
- **Recipient**: a frozen Dotypos customer ID with its resolved locale and delivery status. No email is stored; delivery re-reads the Dotypos profile email and, for marketing, the consent.
- **Test send**: mail to admin-chosen addresses (the admin inbox always included), one email per covered locale, with `[TEST]` in the subject. It isn't a campaign delivery.
- **Confirmation code**: the code each test email carries. The real send needs it typed back. It's bound to the content hash (subject, preheader, bodies, template, purpose), expires after 24 hours, and a newer test send supersedes it. Five wrong codes also supersede it.

- **Evaluation context** (`AudienceEvaluationContext`, `backend/audience-evaluation-context.ts`): the evaluation time, the evaluating campaign (resolves `This`) and the trigger (`at`). One-off sends and previews use `audienceEvaluationAt(now)`. Fact requests are concrete per context (periods become bounds, campaign sources a campaign ID), so subjects with different contexts share a lookup only when the concrete requests agree; evaluation looks facts up with each subject's own context.
- **Scope**: `AudienceFactsService.resolve` and `CampaignRecipientService.resolve` take an optional `scope`: `All` (the default) or `Customers` ids, pushed into every local query. A scoped customer's facts equal the unscoped ones.
- **Reader-first shapes**: saved audiences, and so one-off campaigns, refuse `firstVisit`, `Past`, `TriggerWindow` and any `campaign` with `AudienceFilterContextInvalid` (code `audience-filter-context`) through `audience-filter-usage.ts`; the builder menu hides attributes they can't hold. Stored filters with these shapes still decode, evaluate and summarize. Lift one by removing it from `savedAudienceUnavailableUses`; `TriggerWindow` and `This` stay automation-condition only.

## Recipient resolution rules

- The candidate pool is the customers Workspace knows: reservations ∪ account links ∪ consent rows. Marketing narrows it to active consents.
- Local conditions run first with three-valued logic: Dotypos conditions are `unknown` until hydration, and a candidate local facts already rule out never reaches Dotypos.
- Survivors hydrate with `DotyposService.getCustomers` in sequential chunks of 100. Any Dotypos failure fails the whole resolution with a retryable `CampaignRecipientResolutionError`; never freeze a partial list.
- Count and date attributes resolve once per distinct request before evaluation (`AudienceFactsService`); a candidate without records counts as zero, so `= 0` and `< N` match customers with no reservations or emails. Counts are evaluated within the pool only.
- A visit-basis count over `Past` counts only visits that have started; over any time it also counts upcoming bookings.
- `reservationCount` with the `booking` basis counts booked reservations by the local `reservation_confirmed_at`, so unconfirmed reservations never fall in a booking period. The `visit` basis lists Dotypos reservations starting in the period, then counts the matching local ones; any time counts locally. Without a status only booked reservations count: confirmed and never cancelled, including ones whose fulfillment failed; abandoned and expired checkouts do not. An explicit admin status group replaces that default.
- `campaignEmailCount` counts recipients whose status shows Resend accepted the email (`sent`, `delivered`, `complained`, `unconfirmed`), dated by the first request of the batch that carried them in their current delivery attempt, or by their status change when no batch did. Only campaign emails count: transactional emails have no per-customer record.
- `lastVisit` and `firstVisit` are the start of the customer's latest and earliest booked reservation that has begun. One Dotypos range query serves every last-visit condition: from a week before the earliest Workspace reservation was created up to and including the evaluation time. Never query a customer's whole history, and never leave a visit query's start open: a period without its own start takes that local lower bound.
- A visit starts at its booked start. Dotypos holds an early-setup meeting room from the setup lead before it, so live visit queries start that lead early, read the listed reservations' early-setup details in one query (`CampaignCandidateRepository.earlySetupDetails`), and keep the visits whose booked start falls in the bounds. `ReservationVisits` decodes each visit with the stored details its link rows select.
- `accountCreated` is `customer_accounts.created_at` of the customer's account with a verified login, never the login's own `created_at`. An account is created when its login is. #764's backfill dated accounts for older logins at the backfill time; PR D's migration (`20261021164704_automation_account_creation`) repaired them to the login's time. It also moved each such account's `account-created` event to that time. A repaired linked account with no event got an already-processed one, so the capture reconciler never records a retroactive event. An `account-created` event's `occurred_at` always equals the account's `created_at`.
- Existing customers are old accounts (D37). #764 gave each a silent, unverified login without a session, and both carry the backfill time, so no real creation date exists. The same migration marks these accounts `customer_accounts.legacy`, linked or not: a link the backfill lost to a conflict (`link_conflict`) leaves the account unlinked until a later sign-in claims it. The backfill kept no ledger, so classification uses provenance, bounded to the window the backfill could run in: from #764's merge (`2026-10-20T17:32:49Z`) to `2026-10-20T19:10:00Z`. The backfill's admin operation was removed by #765, whose own production deployment failed; the first production deployment without it (#772's, `e0d80a9d0`) was ready at 18:49:15Z, and the backfill wrote logins only within admin requests, so the end leaves a margin over Vercel's longest function duration. Inside the window, the only other login writer is Better Auth's verified sign-in, which creates the login with its first session. A live login created inside the window is legacy when it is unverified, or has no session from its first ten seconds (a backfilled login verified later opens its first session then), or, when linked, authors a Workspace reservation older than itself (only the backfill assigned those) or has no `account-created` event (every sign-in claim since #757 records one with its link). A genuine sign-up from the window whose first session has since ended is also marked legacy; that safe direction costs it a welcome, never welcomes an existing customer. A login outside the window is never legacy: an older one predates #764, and a later one can't be the backfill's, even a sign-up the migration finds between its verified login and its first session or claim. The production backfill ran once, made 53 silent logins, and had no `link_conflict`. Classification runs before the repair, which skips legacy accounts; a legacy account's existing event keeps its account's `created_at`. Nothing creates legacy accounts any more; every writer inserts the default `false`. A legacy account never fires `account-created`: `CustomerAccountLinkRepository.claim` records no event when it links a legacy account, and the capture reconciler skips it. Intake re-checks `triggeringCustomerEvent` at commit under the accounts' `FOR SHARE` lock (`lockTriggeringCustomerEvents`), so a marking during the profile fetch drops the event. A deployment still running the older reconciler can record one, and historical ones exist, so live intake (`matchIntakeEvents`) and the dry run's replay (`replayEventCondition`) both read events through `triggeringCustomerEvent` (`automation/backend/automation-triggering-events.ts`), which excludes a legacy account's events: intake marks such an event processed without a receipt, and replay neither counts nor replays it. For `accountCreated` it was created before records began (its stored `created_at`), at every replayed moment: once verified, it falls in a period without a start (any time, any time so far, until D) and in one that ends before records began, and never in one that holds any later time, such as the last N days. Don't infer it from verification or dates.
- Locale: linked account → latest reservation → consent → `cs-CZ`. The locale condition filters on the same value.
- Excluded with a reason: missing from Dotypos, deleted customer, missing email, invalid email (`reservationCustomerEmailSchema`).
- Duplicates by trimmed, lowercased email: mail the customer who reserved most recently, then the lowest ID, and report the group.
- Outside production, refuse any send (test sends included) when a recipient is outside `@deskohub.test` (`ensureCampaignRecipientsAllowed`).

## Confirmation rules

- Store only an HMAC of the code, keyed by an HKDF derivation of the first `BETTER_AUTH_SECRETS` entry. A salted plain hash of the 40-bit code would fall to an offline search. Rotating that secret invalidates outstanding codes, so the admin repeats the test send.
- `confirm` locks the campaign row (`for update`) and, in one transaction, checks Draft, recomputes the content hash, consumes the code, and moves the campaign to Sending. Content edits update the same row, so they wait for the lock and then fail as read-only. `issue` takes the same lock before replacing the current code.
- A typed code other than the live current one counts a failed attempt against it. The fifth supersedes it (`too-many-attempts`). A rejection is returned out of the transaction rather than failing it, so the counted attempt commits.

## Send pipeline rules

- `CampaignSendService` (`backend/campaign-send.service.ts`) is the API the admin UI and CLI call: `testSend`, `send`, `retryUndelivered`, `getSendStatus`, and `adminInbox`.
- `send` resolves recipients and runs the test-domain guard before it touches the code. Then one `confirm` transaction consumes the code, moves the campaign to Sending, and inserts the send (audience ID and filter snapshot, content hash) with its recipients. A resolution or guard failure leaves the Draft and its code usable.
- Delivery runs in the `workspace-email-campaign-send` Vercel Queue consumer, one message per delivery attempt (`{ sendId, deliveryAttempt }`), retained for 48 hours. The next 100 pending recipients that no batch carries yet, in customer ID order, are re-read and rendered. Then the batch is persisted in `email_campaign_delivery_batches` (`requested`, with its recipient IDs in message order and a SHA-256 of the exact payload) **before** its Resend request under the key `email-campaign:<sendId>:attempt-<n>:batch-<i>`. Never rebuild a batch from the recipients still pending: a webhook or a lost DB write would change the payload, and Resend rejects a key reused with a different payload.
- At delivery, each recipient's Dotypos email (and, for marketing, active consent) is re-read with the resolution's rules (`reachableCampaignEmail`). Outside production, the test-domain guard then applies to the email read at delivery. A recipient who fails any of these is `skipped` with a `skip_reason`, and is never part of a provider request.
- One run at a time delivers a send. A run takes the send's lease (`delivery_lease_id`, `delivery_lease_expires_at`, 300 seconds) before it replays or prepares anything and releases it however it ends; a message that finds another run's unexpired lease fails and waits for its redelivery. Every write the run makes (persisting a batch, settling a batch, failing unprepared recipients, settling the campaign) runs in a transaction that first locks the send row and checks the lease is still this run's, so a run that stalled past its lease writes nothing. An accepted batch moves its `pending`, `failed`, and `unconfirmed` recipients to `sent`.
- `EmailService.sendBatch` makes exactly one request; it never retries internally. Only the campaign's persisted replay retries a batch, because only it knows an earlier request may have been accepted. A retry inside the request would turn a lost acceptance followed by a 429 into a refusal.
- `EmailServiceError` means Resend refused the request and sent nothing (a 4xx other than 409). `NetworkError` means the outcome is unknown: a timeout, a 5xx, a 409 (key already used), or an unreadable response to an accepted request. A refused first request makes the batch `rejected` and its recipients `failed`. An unknown outcome leaves the batch `requested` and fails the message. Each later run first replays every `requested` batch: it re-reads and re-renders the members, and resends only when the payload hash matches, under the same key. A batch becomes `unconfirmed` (with its still-pending recipients) when its payload changed, when a replay is refused, or when 23 hours have passed since its first request, an hour inside Resend's 24-hour key window. It is never resent under a new key automatically.
- Resend requests time out after 5 seconds (10 for a batch) in production and 30 seconds elsewhere (`VERCEL_ENV`). A run starts no batch after 120 seconds and gives up at 270, inside the 300-second limit. A run cut off mid-request loses nothing, because its batch is already persisted and is replayed.
- The campaign ends Sent, or Failed when any recipient is `pending`, `failed`, or `unconfirmed`. `retryUndelivered` moves `pending` and `failed` recipients into a new attempt. It moves `unconfirmed` ones too only with `includeUnconfirmed`, because they may already have the email. Sent, delivered, bounced, complained, and skipped recipients are never mailed again.
- Marketing emails carry `List-Unsubscribe: <…/api/email-campaigns/unsubscribe?token=…>` and `List-Unsubscribe-Post: List-Unsubscribe=One-Click`, and the footer links to the same URL. The token is an HMAC of the send ID and customer ID, keyed by an HKDF derivation of `BETTER_AUTH_SECRETS` (every listed secret verifies it). POST withdraws an active consent and is a no-op when repeated. GET never unsubscribes; it issues a marketing-management token and redirects to the preferences page. There is no `mailto:` unsubscribe because no inbox processes those requests. Operational emails carry no unsubscribe headers.
- Campaign emails carry the Resend tags `category=email-campaign`, `campaignSendId`, `dotyposCustomerId`, and `deploymentEnvironment`. `campaignEmailKind` in `campaign-email-message.ts` declares the category and tags, and the Resend webhook's delivery report ingress routes their reports to `campaignDeliveryReports`, which records them through `CampaignDeliveryStatusService`. It matches the recipient by message ID, or by tags when the event beats the stored ID, and only moves status forward (`delivered`, `bounced`, `complained`). The event proves delivery, so it also settles a `failed`, `unconfirmed`, or `skipped` recipient. Bounces and complaints never touch consent; Resend's suppression list handles them.
- Test emails go only through `EmailService.send`, with `[TEST]` subjects and the code above the body. They create no send rows. Outside production the code is also logged, because preview inboxes are Console-only.
- `EMAIL_CAMPAIGN_FROM`, `EMAIL_CAMPAIGN_REPLY_TO`, and `EMAIL_CAMPAIGN_ADMIN_INBOX` configure the sender and the admin inbox. Production fails campaign operations with `CampaignEmailNotConfigured` until all three are set. Elsewhere unset values fall back to `@deskohub.test` addresses.

## Body images

- The editor uploads a body image straight from the admin's browser to Cloudinary; no image bytes pass through a Server Action or Vercel. `authorizeCampaignImageUpload` (admins only) returns `CampaignImageService.authorizeUpload`: fields signed by `CloudinaryService.signImageUpload` with `api_sign_request`, valid for an hour.
- The signature fixes the folder `campaignImageFolder(VERCEL_ENV)` (`email-campaigns/<VERCEL_ENV>`, defined in `body/campaign-image-account.ts`), a fresh UUID public ID, `overwrite=false`, `allowed_formats=gif,jpg,png` with `format=png` for anything else, and the incoming transformation `campaignImageTransformation` (`c_limit,fl_force_strip.lossy,q_85,w_1068`). Incoming transformations keep metadata unless `fl_force_strip` is set; `fl_lossy` stores a PNG without an alpha channel as a JPEG. `resource_type` isn't signed, but save-time rules accept only `/<cloud>/image/` URLs.
- Only a still file above the account plan's `media_limits` (Free: 10 MiB, 25 MP, 50 MP across an animation's frames; read with one Admin API `usage` call) is first shrunk on a canvas in the browser (`shared/browser/image-downscaling.ts`). The canvas keeps only an animation's first frame, so an animation above the limits (frames counted by `shared/utils/image-animation.ts`) is refused with a message instead.
- The editor accepts an answer only for the authorized public ID with a valid width. Save-time rules (`isCampaignImageSource`) stay the gate for every adapter.
- `CampaignService` create, update and patch also refuse an image the content adds unless `isUploadedCampaignImage` holds: an untransformed `/<cloud>/image/upload/[v<n>/]email-campaigns/<any environment>/<name>` URL. An image already anywhere in the stored content stays valid, so older bodies and `dhw` export→import round trips keep working; the body schema itself doesn't check folders, so stored bodies decode as before. The refusal (`CampaignImageNotUploaded`) reaches clients as the existing `content-invalid` code, which released `dhw` binaries know.

## Automation engine timing

- The planner ticks every `emailAutomationTickMinutes` (`@deskohub/workspace-admin-api`). Units it plans run from the queue seconds later, still within the tick.
- Engine health's sweep lag reads only the clock-following `reservation-activity` cursor. The hourly `reservation-activity-reconcile` cursor records when its last window opened, so it is up to an hour old on a healthy engine and would raise `sweep-lagging` every hour.
- The reconcile has its own freshness, `reconcileLagSeconds`: the time since its last completed window opened. The cursor moves only after a window's last page, so a window stuck on a failing page keeps the lag growing. `reconcile-stalled` fires above 2 hours plus a tick (135 minutes), and also when the reconcile has no cursor row, because the sweep only pages sources that have one. One missed hour doesn't warn, just as one missed tick doesn't raise `planner-stale`. A missed hour is not lossless, though: the next window starts an hour later, so a visit moved near the old window's 24-hour edge can slip past both. Keep the warning logic in `AutomationEngineHealth`; the run log and `dhw` only render it.
- Engine lock order (`automation-lifecycle-lock.ts`, §5.4): lifecycle lock, triggering reservations `FOR SHARE`, run rows in id order, send/recipient/batch rows, unit rows, then the slot lock. Intake's commit alone first locks all its events' `customer_accounts` rows `FOR SHARE` in id order, in one statement, before any lifecycle lock, so a legacy marking during the profile fetch is seen at commit; account writers take no engine lock. Settling a unit frees its run rows before its CAS locks the unit row. A hand-off can already hold `planned` rows (a preview dropping its siblings, or a follow-up upsert that hits an existing key) when it asks for the slot lock, so slot promotion (`fillAutomationUnitSlots`) selects candidates `FOR UPDATE SKIP LOCKED` and never waits for a unit row under the slot lock; the next hand-off or top-up promotes a skipped unit.
- Both engine advisory locks are registry operations: the fire-entry lock (`WorkspaceLocks.automationFireEntry`, through `lockScheduleFireEntry`) comes before the lifecycle lock, and the slot lock (`WorkspaceLocks.automationUnitSlots`) is always last. A handler's `commit` and `expire` and a send's settlement require `WorkspaceTransaction`, and the processor runs them in `AutomationUnitSlots.handOff`, which opens `withTransactionPermit(transaction(...))`. `fetch` and `submit` run outside any transaction; nothing in their types proves it.
- Only waits take time (D36). Whatever moves a run onto a step handles that step in the same transaction through `automation/backend/automation-reached-step.ts`. That covers the unit that enters a run (`enterAutomationRuns`, from `intake` and `fire-chunk`), a condition unit's commit, and the timer pass for the step after a wait it completes.
  - A Condition gets condition units.
  - The Send gets deliver units. The timer pass leaves both to the same tick's condition and send planning.
  - A wait is evaluated on entry by `evaluateStep` (`enterReachedWaits`). If it already holds or is due, the run goes on to the next step. Otherwise it is stored `waiting` with its due time.
  - So a run goes through its conditions and due waits to a pending wait or its send within the tick it entered or woke on.
- Steps count their depth in a chain, carried in a condition subject's `chainedSteps`. Past `maxChainedSteps`, one less than the flow step limit, runs stay `ready` for the planner. Valid flows never reach it.
- Wait anchoring, due checks and the intake cutoff use the tick's nominal instant, `automationTickAtOrBefore(at)` (`automation/automation-ticks.ts`): the planner's or unit's clock rounded down to the tick grid, so cron jitter within a tick doesn't move them. Audience and condition evaluation still use the actual time, and a unit that runs past a tick boundary anchors at the later tick.
  - The planner takes in only events that occurred at or before its tick; a later event waits for the next tick. A run therefore enters on a tick at or after its trigger, as in the dry run. A backlogged entry anchors at the tick that processes it.
  - A Duration wait counts from the tick it was entered in, and a Calendar wait is evaluated at that tick.
  - A wait is due when `dueAt <= tick`, in both `evaluateStep` and the timer planner's due query. There is no early tolerance: a wait completes on the first tick at or after its due time, never before.
  - A Calendar wait whose due time a pause passed over is re-evaluated from the later of the tick and the resume.
  - A deferred send is rechecked one tick after the tick that deferred it.
  - Recorded transition times stay actual.
- Engine Postgres tests drive this with `scenario.tick` (plan, then drain) or `runUntil({ onTicks: true })` (the cron's cadence). An event must occur at or before the tick a test plans it in, or the test plans on the next tick. `planUntilQueued` holds units of one kind back so that a test can act between entry and the next step. Use `sameInstant` only for work that a later planner run picks up.

## Automation trigger re-check

- Intake, the dry run's replay, and the deliver unit's pre-submit check judge a reservation trigger by its live Dotypos visit through one pure verdict, `triggeringVisitVerdict` (`automation/automation-trigger-verification.ts`): `current`; `withdrawn` when Dotypos cancelled the visit or no longer returns it (D28); or `moved` when a started trigger's visit now starts after `asOf`, or a finished one's ends after it. A booked trigger needs only an active visit. `readsTriggeringVisit` says which kinds are re-checked and `withdrawnByCancellation` which ones a Workspace cancellation withdraws; a cancellation trigger is the cancellation itself, so it is never withdrawn. Both match every trigger kind, so a new kind is decided there, not in each caller.
- Each path picks its own `asOf` and names the verdict in its own terms:
  - Intake compares with `now`, when it re-reads the visit. `moved` supersedes the event without a receipt, because the sweep records a new event at the visit's new time.
  - Replay compares with the event's stored `occurredAt`, since it replays intake from today's visits without knowing when intake would have run. `moved` hides the event, `withdrawn` withdraws it before entry. So an event whose visit was extended and has since ended still enters live, if otherwise eligible, but is hidden in the replay, which replays the sweep's later event instead. Replay passes the visit's instants and `occurredAt` through `toStoredInstant`. It skips the re-check for a reservation Workspace cancelled and leaves it to the replayed pre-submit check, which knows when the cancellation fell.
  - The pre-submit check compares with the send instant. `moved` defers the send, `withdrawn` withdraws the run.
- Request costs count a trigger's reservation only when `readsTriggeringVisit` holds for its kind: intake planning, the dry run's replay chunks, and send planning's deliver units.

## Automation dry run

- Dry-run times are engine ticks (`automation/automation-ticks.ts`): `simulateRun` enters a run on the first tick at or after its trigger, checks a wait on the tick it enters it, and otherwise completes it on the first tick at or after its due time, with the engine's rule (`evaluateStep`). Replay holds off an event whose intake tick is at or before the open run's end tick.
- A replay row is `reservationStatusesApproximate` when the entry audience or a condition decided it before the customer's latest undated status change, or when it depends on such a row: `replayCustomerEvents` keeps the latest end tick an approximate row's run could reach (every condition matching) and marks later events taken in by then, and, when the flow counts this campaign's emails, every later decided row.
