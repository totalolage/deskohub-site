# Deskohub Workspace referrals

Read the business-facing [referral specification](../../../apps/deskohub-workspace/docs/referrals.md) before changing referral eligibility, attribution, discount, or payment behavior. Treat it as the policy source; keep implementation guidance here.

## Release flag

The whole program sits behind the PostHog boolean flag `referrals` (generated contract key; see the `deskohub-workspace-feature-flags` skill). Only `true` releases it; an error, timeout, or missing flag counts as off and is logged.

- Turn it on per deployment with `POSTHOG_FEATURE_FLAG_OVERRIDES` (`"referrals":true` in the map): `.env.development` sets it for local development, and the protected Preview environment must include it for the E2E referral lane. Production rejects overrides, so production follows the PostHog flag; keep it inactive there until launch.
- Decide once per request and give every consumer that decision, so a page gate and the services it calls never disagree:
  - Server Components and actions read `areReferralsEnabled()` (`referral-feature-flag.server.ts`, React `cache`, any failure counts as off), evaluated after `connection()` inside a Suspense boundary on Cache Components pages.
  - Every Next.js boundary that runs referral Effect code (page loaders, Server Actions) provides `ReferralFeatureFlagRequest`, which hands that same decision to `ReferralFeatureFlagService`. `ReferralService.Live` requires the service and never evaluates the flag itself.
  - React `cache` does not memoize inside a Server Action or route handler, so call `areReferralsEnabled()` only from Server Components (or through `ReferralFeatureFlagRequest`, built once per run). Helpers on action and route paths read `ReferralFeatureFlagService` or take the decision as an argument; they never evaluate the flag again.
  - Outside a request (queues, webhooks, cron), `ReferralFeatureFlagService.Live` evaluates once per layer build. Never put it, or `ReferralService` or anything else built over a request's decision, in a process-wide runtime layer or memo map: `makeDiscountServiceLayer` caches only the request-independent discount providers and release gates per process and builds the referral and discount services per run.
  - Tests pick the value with `ReferralFeatureFlagServiceMock({ isEnabled: Effect.succeed(bool) })`; `WithheldReferralService` (`referral.service.mock.ts`) is the real service with the flag off and no data access.
- A withheld program, or an unreadable flag, is never a verdict on a code or customer. `acceptReferral`, `findAvailableCode`, `evaluateCheckoutReferral`, and `getAccountSummary` fail with `ReferralError` reason `disabled`, distinct from `unavailable` and from an unusable code. A stored signup intent stays pending on `disabled`, profile completion ignores the code, the auto-link logs and skips, and checkout answers with its generic `unavailable`.
- While off, enforcement is server-side at every seam:
  - `ReferralService` treats no code as a referral code (`lookupCodeKind` → other, so the checkout box answers like any unknown code), prices no invitation or referrer discount, reports nothing settled, issues no code, and fails code lookups, checkout evaluation, the account summary, and acceptance as `disabled`.
  - `RememberedReferral` reads no code and writes nothing, so no prefill, auto-apply, settlement check, or cookie clearing runs; the client capture is not mounted.
  - The account hides the Referrals section, nav item, and badge (`/account/referrals` is not found), drops the completion field and ignores a submitted code, and skips the auto-linked acceptance, the signup-intent retry, and the notice; the acknowledge action requires the flag.
  - The flag gates new referral pricing and admission only. A referral already admitted into an order's invitation claim while the flag was on is honored at payment: every paid path (`markPaid`, `completeInternalPayment`, late-recovery settle, from requests, webhooks, queues, or cron) redeems the claim and records its attribution whether the flag is on, off, or unreadable, taking the graph lock first as usual. The payment repositories therefore never read the flag. With no admitted claim, nothing is attributed.
  - Existing attributions, intents, and claims stay untouched and apply again once the flag is back on. Admission still serializes an attributed invitee's first booking.
- The proxy cannot evaluate the flag: flag classification is a `"use cache"` function, which the Next.js proxy does not support. It therefore only hands a shared code to its own request's render and never stores it.

## Public boundaries

- `features/referrals/client.ts` is browser-safe. Use `parseReferralCode` for untrusted values and `referralCodeQueryParam` for the `ref` search parameter of share links.
- Remembered shared code (`features/referrals/referral-code-cookie.ts`):
  - `RememberSharedReferralCode` (mounted in the locale root layout through `RememberSharedReferralCodeWhenEnabled`) stores a syntactically valid `?ref=` from the shown page in the first-party `deskohub-referral-code` cookie (Path=/, SameSite=Lax, Secure over https, not HttpOnly, `sharedReferralCodeRememberedDays`). It is the only capture: `proxy.ts` cannot read the referral flag (see "Release flag"), so it never stores the code.
    - It stores the code only when the browser has none yet, through the shared `findSharedReferralCodeToRemember`, `setReferralCodeCookie` and `browserCookieJar` (`referral-code-cookie.ts`). First-wins is best-effort: simultaneous first visits with different codes each set the cookie, and the last one applied wins.
    - A page Chrome prerendered is remembered once `document.prerendering` is false or on `prerenderingchange`.
    - It remembers only in the top-level browsing context (`window.self === window.top`), never inside a frame.
    - So the landing page's own render can use the code, `proxy.ts` hands it to that request only (`request.cookies.set` with forwarded request headers, no `Set-Cookie`) for a real top-level document GET while none is remembered. It skips non-GET requests, Next.js router and prefetch requests (`rsc`, `next-router-state-tree`, `next-router-prefetch`, `next-router-segment-prefetch`), speculative loads (`Sec-Purpose`/`Purpose` naming prefetch or prerender), and any `Sec-Fetch-Dest` other than `document`. The gated reader ignores it while the program is withheld.
    - A prerendered page's server render didn't see the code, so its completion prefill may appear only from the next navigation.
    - `remember-shared-referral-code.browser.test.ts` pins prerender plus activation in natively launched Chromium (Chrome won't prerender under Playwright's DevTools control), and a framed page that remembers nothing.
  - Never thread `ref` through links. Every server reader and writer goes through the `RememberedReferral` capability (`features/referrals/remembered-referral.service.ts`), which reads the provided `ReferralFeatureFlagService` decision and owns the settlement rules below. Its operations are `code` (account sign-up), `forBooking` (checkout carry or prefill), `remember`, `forgetIfSettled`, and `isSettled`; only `remember` can fail, and every other failure keeps the code and logs `referrals.remembered-referral.unavailable`. Next.js control flow, such as a prerender that can't read cookies, propagates.
    - Adapters: `RememberedReferral.Cookies` on the site, `RememberedReferral.none` for the AI-agent tools (no browser: nothing read, carried, or forgotten), and `RememberedReferral.inMemory(cookie, { writable })` in tests. Tests provide `inMemory` with the real release gate instead of mocking a module; `writable: false` models a Server Component render or prerender, where Next.js refuses cookie writes.
  - The cookie is cleared once the booker's referral is settled (`ReferralService.hasSettledReferral`: attributed or past a paid booking). The `Booker` says whose referral the code serves: an account page or action passes the linked customer it resolved (`kind: "account"`); checkout passes the order (`kind: "order"`), whose booker is the signed-in account's linked customer, falling back to the booked customer (and a paid order) when the session has none. An unlinked account has nothing to settle. Booking for someone else never clears the booker's cookie. To clear:
    - Server Actions and route handlers call `forgetIfSettled(booker)`;
    - Server Component pages call `isSettled(booker)` and render `ForgetRememberedReferralCode`, because they can't write cookies.
  - Settlement is checked only when a code is remembered.
  - A code typed in the completion field or the checkout box always takes precedence. A typed checkout referral that is accepted or already accepted is written with `remember` in the discount action, replacing any stored code, so an order edit keeps it; a failed write is logged and the accepted pay state stands. Rejected codes are never stored.
- `features/referrals/index.ts` exports `ReferralService`; `ReferralError` and the public referral types live in `features/referrals/contracts.ts`. Use `ReferralService.Live` for production composition. `lookupCodeKind` is a pure registry lookup; it may distinguish referral from ordinary codes but must not issue a code or change attribution. The reads that fan out across Dotypos and the database (customer history, invitees, savings, the account summary) live in `features/referrals/referral-standing.ts`, which opens no transaction; `ReferralService` keeps its transactions free of concurrency and reads history inside one with `loadCustomerHistoryInTurn`.
- `getAccountSummary` is an explicit account read that may create the customer's durable share code. Do not call it from quote or checkout pricing.
- `findAvailableCode` is a read-only check that returns the canonical code only when it is an enabled, currently valid referral code whose owner has a linked account without pending deletion. Use it to validate or prefill a code before any write; it never issues codes or attributions.
- `evaluateCheckoutReferral({ code, dotyposCustomerId })` is the read-only checkout eligibility check for the booked customer. It returns eligible or already_accepted, or a rejection reason. Pricing (`resolveInvitationCandidate` with an optional carried `referralCode`) prices the invitation from an existing attribution first, otherwise from a still-valid carried code.
- `acceptReferral` is the only immediate attribution mutation, used by the account sources. Checkout attribution is recorded by the payment lifecycle (see below). `acceptReferral` validates the linked Dotypos identity and active referrer, then writes the permanent relationship. It is idempotent for the same referrer and rejects with distinct reasons: `already_attributed` (changed referrer), `self_referral`, `cycle`, `ineligible` (a paid booking exists, so the window is closed), and `pending_payment` (no paid booking yet, but a payment is in progress). A claim is reserved only in the transaction that makes the reservation `pending`, so the pending check covers active claims. `evaluateCheckoutReferral` reports the same distinctions; checkout shows `pending_payment` and `cycle` as generic `unavailable`. It takes the account advisory lock in its own transaction, so never call it while another account lock or transaction is held.
- Only these callers may attribute, matching the business sources:
  - First-time profile completion (`features/account/actions.ts`, create branch only): the code is checked with `findAvailableCode` before the profile is created. A typed unusable code returns `referral-code-unavailable`. A code that matches the server-supplied prefill (`prefilledReferralCode`) and has become unusable is dropped silently.
    - The link claim writes a `referral_signup_intents` row (`features/referrals/signup-intent.repository.ts`) in the transaction that inserts the link, and only when that claim creates it. A losing concurrent completion stores nothing and reports from the account's state.
    - `recordSignupReferral` (`features/account/backend/signup-referral.ts`) runs `acceptReferral` after the lock is released.
      - An unsettled intent (`settled_at` empty) is retried on every linked account load. A transient failure or `pending_payment` leaves it pending.
      - A definitive outcome, including `cycle`, is stored with one conditional `settle` update (`where settled_at is null`), so concurrent loads settle it once and a loser reports the stored winner.
      - A settled intent is never retried. Its stored outcome is reported on every load, so an abandoned response or a second tab is harmless.
    - The loader carries the stored outcome as the linked state's `signupReferral`. `ProfileCompletionReferralNotice` renders only from that server state.
    - A settled outcome shows until the customer dismisses it through `acknowledgeSignupReferralNotice`, which sets `acknowledged_at`. Nothing client-side keeps an outcome, so a refresh can't revive stale feedback.
    - An already-linked account ignores the code.
    - The account page prefills the field from the remembered cookie only in the completion-required state, and only when `findAvailableCode` returns it.
  - Auto-linked first sign-in (`features/account/backend/auto-linked-referral.ts` `acceptAutoLinkedReferral`, from the account page loader). When `CustomerAccountResolver.resolveLink` reports `autoLinked` (this resolution claimed the link to an existing customer) and the browser remembers a shared code, it calls `acceptReferral` after the resolver lock is released. Failures are silent. Opening the magic link in a browser without the cookie misses the attribution.
  - Checkout, for the booked customer of any booking (the account's own customer or someone else). It carries the referral in the signed pay state (`referralCode`), prices it, reserves the invitation claim with its referrer and code at admission, and records the attribution in the transaction that marks the order paid. Sources:
    - the checkout code field, through `CheckoutReferralService`;
    - the remembered cookie, read in `prepareWorkspacePayState`:
      - An account booking for the customer themselves evaluates the code and carries it into the first pay state, adding the `referralApplied` marker.
      - Preparation clears the cookie when the booked customer is settled.
      - The paid status page (`checkout-status-referral-code-settlement.tsx`) and the zero-total internal payment clear it too. Nothing is written before payment. For someone-else bookings, a code that `findAvailableCode` accepts becomes the signed pay state's `requestedDiscountCode`, which only prefills the box. A `discountCode` the visitor requested takes priority, and nothing auto-submits.
- Do not add an account-screen or other later acceptance path. The auto-linked first sign-in and the linked-load retry of a stored signup intent are the only account-side cases outside the completion action.
- `features/checkout/backend/checkout/checkout-referral.service.ts` exports `CheckoutReferralService`. Its `acceptCode({ code, payStateToken, locale })` needs no account. It evaluates the code for the reservation's own customer, re-signs the pay state carrying the referral, and returns one of these statuses:
  - `accepted` or `already_accepted`, with an updated signed checkout URL.
  - `already_attributed` (a different existing referrer) or `ineligible` (the first-booking window has closed). The discount action redirects these with `discountCodeError=referral-already-attributed` or `referral-ineligible` (`features/checkout/discount-code-rejection.ts`). Every referral rejection re-signs the typed code as `requestedDiscountCode`, so it stays in the box.
  - `unavailable` or `pricing_changed`. Every other referral failure stays `unavailable`, so the response doesn't reveal whether a code or account exists.
- The ordinary submitted-code slot remains available. Once an ordinary code is applied, the code field closes, so customers enter a referral code first.

## Pricing and snapshots

Pricing is a pure read of accepted attribution and current eligibility. It never creates share codes, accepts referrals, or reserves claims. Apply ordinary and customer discounts first, then the 15% invitation candidate, then the referrer's fixed-money candidate calculated from the exact remaining subtotal. Apply voucher credit after those referral adjustments so credit never reduces the benefit basis. Keep the voucher's independent claim instruction, and ensure its final application and payment commitment match the displayed order and amount.

Compute the referrer reduction as `1 - 19^n / 20^n` over integer minor units using `BigInt`, then round the total monetary benefit once. Never round a per-person percentage or cap the count. Omit a candidate whose rounded value is zero so a payable small subtotal does not fail admission.

Keep invitation and referrer applications distinct, with stable IDs, localized labels, and provenance. The invitation application carries the durable claim instruction; accepted payment snapshots preserve the exact accepted label and amount. Use the shared discount quote and immutable accounting snapshot flow rather than a referral-specific checkout total.

Checkout referral acceptance carries the referral in the pay state, then rebuilds the signed quote. The acceptance seam may treat the first invitation application as the expected price change only when undiscounted items and amounts plus every non-referral application still match. The invitation must be the current customer's exact 15% application. An existing referrer application may recalculate only when its count label and provenance count are unchanged and both fixed amounts match the exact formula on their respective subtotals. Compare the resulting total as well; any unexplained difference, ordinary-code drift, base-price change, or referrer-count change remains `pricing_changed`. A retry with the original signed token uses the same narrow comparison and returns a usable refreshed invitation quote. Keep this comparison private to checkout acceptance.

The discount action owns the validated `referralApplied=1` success marker. It appears only for accepted or idempotently accepted relationships, and the page shows the localized fixed-15% notice only when the signed quote contains the invitation application. Referral input stays out of `submittedCode`; a normal code application rebuilds the URL without the marker.

## Persistence and payment lifecycle

`db/schema/referrals.ts` owns the durable referral code, attribution, and invitation-claim tables. Referral codes are rows in the shared `promotion_codes` registry with explicit `kind = 'referral'`; registry kind, not lexical shape, decides code dispatch. Attribution uses opaque Dotypos customer IDs, so auth-account deletion cannot erase eligibility or payment history. Keep referral claims in their own ledger, independent of ordinary code-redemption claims and vouchers.

`referralInvitationClaims` has one active (`reserved` or `redeemed`) claim per invited customer. Reserve it in the same transaction as the payment attempt and discount applications; redeem on local paid transition; release on failure, cancellation, or expiry. Late recovery must atomically readmit a released claim and reject it when another attempt has consumed or reserved the invitation. Normal first-booking admissions and paid transitions use the same invited-customer lock so an ordinary attempt cannot race past a reserved invitation. A customer counts as invited once attributed or once they hold an active claim. Claims from a checkout referral store `referrer_dotypos_customer_id` and `promotion_code_id`. Admission fails as `claim_conflict` (shown as a price change) when the customer has meanwhile been attributed to a different referrer. The paid transition (`markPaid`, `completeInternalPayment`, late-recovery settle) inserts the attribution from the claim in the redeeming transaction. A different referrer or a cycle that appeared after admission keeps the existing graph, logs a fixed reason, and never fails or undoes the payment. Release paths have nothing to undo. Older claims without these columns rely on their existing attribution. Customers without an accepted invitation retain normal concurrent ordinary payments; customers with prior local paid evidence retain ordinary repeat-booking behavior.

For attribution, open one transaction with `advisoryLock.withTransactionPermit(transaction(...))`, permit outside. Inside it, take `WorkspaceLocks.referralGraph()`, then `WorkspaceLocks.customerAccounts(accountIds)`, then `WorkspaceLocks.referralFirstBooking(customerId)`. Recheck linked identities and account activity, read local booking history and graph state, and insert the attribution. Every statement on `db` inside the transaction joins it, including calls to other Workspace repositories, so no executor is passed. Only Dotypos history retrieval is external. Run it one read at a time, so a Dotypos failure can't interrupt an in-flight query. Don't call account-link methods that open a lock section on another connection (`withAccountLock`) inside the transaction. Payment lifecycle and late-recovery transactions take `referralFirstBooking` before locking reservation or attempt rows, and take `referralGraph` first when the attempt's claim carries a checkout referral. The zero-total internal payment takes its graph lock with a bounded wait (`referralGraph({ boundedWait: Duration.seconds(5) })`), so it fails with a lock timeout after five seconds instead of waiting on. A signed-in checkout runs it inside the account guard, which holds the account lock on another connection; there the graph lock is out of rank order, allowed because the section holds the higher-ranked account lock. A guest checkout runs it without a guard, where the graph lock is in order and the same bound applies. The registry checks this order on admission, paid, terminal-release and recovery paths.

## Tests and migration

Referral codes live in the `sensitiveText` promotion `code` column, so the query log censors their lookups; `db/schema/sensitive-columns.test.ts` covers the column. Keep exact-money and eligibility rules in focused pure tests. Use service Postgres tests for concurrent cycle acceptance, active-account checks, Dotypos/local-history evidence, and auth deletion or relinking. Use checkout lifecycle Postgres tests for both admission orders and races, ordinary-code/voucher coexistence, terminal release and retry, consumed claims, and late-recovery conflicts. Run database suites serially against the disposable `WORKSPACE_TEST_DATABASE_URL`.

Generate additive schema changes with `bun run db:generate` from `apps/deskohub-workspace` after the final schema is stable. Keep the generated migration, snapshot, and journal produced by Drizzle tooling together; never hand-edit generated migration metadata.
